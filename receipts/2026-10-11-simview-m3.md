# M3: scripted touch frames drive state and re-render on Linux

2026-10-11. `simview/` on branch `simview-m3`. The runner loads a frames
file and validates it. It hit tests on the laid-out frames. It fires button
actions under the touch rules of `docs/SIM-INPUT-MODEL.md`. It writes
`@State` and re-renders after every frame. The final render goes to a PNG.
No GPU, no Mac, no phone. All our own code. The demo app
`sdk-free/swiftui/HelloApp.swift` is unchanged.

## What was built

- `App.main()` gains `--frames`. Without it, the app renders once, as in M2.
- The frames loader accepts frames of finger records and the short form
  `{"tap": [x, y]}`. The short form expands to a began frame and an ended
  frame 80 ms apart. It refuses out-of-order `t_ms`, empty `fingers`, and
  bad records, and names the frame index.
- One layout pass now places every node. The draw pass and the hit testing
  read the same placed rects, in draw order. Buttons get ids in tree order:
  `Button#1`, `Button#2`. A button draws its label only, as in M2. The hit
  area is the label rect.
- The touch rules: the topmost element under the first finger at `began`
  owns the whole touch. It keeps the touch when the finger leaves. All
  fingers of one gesture share that target. The action fires only when the
  last finger ends inside the target. A `cancelled` finger kills the
  gesture.
- `@State` stores its value in a reference cell. Copies of a view share one
  box, so the action closure writes what the next render reads. The setter
  stays `nonmutating`, which is why `{ count += 1 }` compiles unchanged.
- The runner prints each button rect, then one log line per finger record,
  after the frame's re-render succeeds.
- Font: the five descender glyphs `g j p q y` gained two rows below the
  baseline. Now `taps` and `tap me` read correctly. Text with a descender
  measures 9 points tall. This changed the M2 golden; `golden/demo1.png` was
  regenerated. The new golden `golden/after-tap.png` holds the demo render
  after one tap.
- `simview/Sources/M3App/M3App.swift` is the second app the test rows need.
  It has two buttons. Button#1 carries the state in its label, so a tap
  changes pixels inside the button box. `simview/test-m3.sh` runs the eight
  spec rows, the demo tap, the negative control, and determinism. Their
  expected results, committed before the input code, are in
  `simview/TESTS-M3.md`.

## Build host and commands

A Linux x86_64 container. Swift 6.4 lives inside an Arch chroot. The chroot
is reached through a private copy of the repo arch runner, with this
worktree bound at `/work`:

```sh
$ cp ~/tmp/apple-dev/archrun.sh ~/scratch/apple-dev/simview3/archrun.sh
$ sed -i 's#^W=.*#W=$HOME/src/omarchy-apple-dev-wt-simview3#' \
  ~/scratch/apple-dev/simview3/archrun.sh
$ export SIMVIEW_CHROOT_RUN=$HOME/scratch/apple-dev/simview3/archrun.sh
$ bash simview/build.sh
built /work/simview-demo and /work/m3app
```

One tap of the demo app. The runner prints the button rects first, then one
line per finger record:

```sh
$ $SIMVIEW_CHROOT_RUN --user '/work/simview-demo --frames /work/simview/build/golden-tap.json --out /work/simview/build/after-smoke.png'
button id=1 rect=177,430,35,9
t=0 finger=0 began (194,434) target=Button#1 state=count:0 render=ok
t=80 finger=0 ended (194,434) target=Button#1 state=count:1 render=ok
wrote /work/simview/build/after-smoke.png 390x844
```

The no-tap render and the after-tap render differ in 19 pixels. All 19 sit
in the `taps: 1` glyph box at x 210 to 214, y 405 to 410. The demo button
label is static. Its box does not change. The m3app app covers the in-box
row:

```sh
$ $SIMVIEW_CHROOT_RUN --user '/work/m3app --frames /work/simview/build/smoke-m3.json --out /work/simview/build/m3-after.png'
button id=1 rect=180,410,29,9
button id=2 rect=180,435,29,7
t=0 finger=0 began (194,414) target=Button#1 state=count:0 render=ok
t=80 finger=0 ended (194,414) target=Button#1 state=count:1 render=ok
```

That render differs from the no-tap render in 38 pixels. 19 of them sit
inside the Button#1 rect: the `tap 0` label became `tap 1`.

I viewed both goldens in the image viewer. I also viewed an 8x zoom of the
text block. `taps: 0`, `tap me`, and `taps: 1` read cleanly. The `p` stems
drop below the baseline.

The suite ends with `simview/test-m3.sh: all rows passed`. Exit 0 means
every row passed.

Row 7 error text on stderr:

```
frames: frame 1: t_ms 200 goes backward (previous 400)
```

Tolerances, stated in `simview/TESTS-M3.md`: log comparison is exact bytes.
PNG comparison is `simview/compare.py`: 0 differing pixels, 0 per-channel
difference. Row 0 checks the after-tap render against
`golden/after-tap.png` at that tolerance.

Regression. `bash simview/test.sh` passes: identical bytes across two
renders, and the changed-initial-state negative control still fails the
compare as required. It compares 0 differing pixels against the regenerated
`golden/demo1.png`. `bash tests/run.sh` passes end to end, exit 0, with
`simview/test-m3.sh` added to it.

First run notes. Two test script bugs failed the first run and were fixed in
place. The rect parser split on commas, so bash arithmetic read the tap
point as 9,0. Row 8 compared logs that contain the output path, which
differs between two runs. No input code changed for those fixes.

## Not claimed

- No iOS gesture recognizers. The hit testing and the touch rules are ours.
- No scroll, fling, pinch, rotate, or momentum. The frame format fits them;
  the runner does not.
- No keyboard, no focus, no text input.
- No timing feel. Times come from the file, not from a clock.
- No proof about Apple's renderer. The draw path is ours.
