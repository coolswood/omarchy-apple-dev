# M3: scripted touch frames drive state and re-render on Linux

2026-10-11. `simview/` on branch `simview-m3`. The runner loads a frames
file and validates it. It hit tests on the laid-out frames. It fires button
actions under the touch rules of `docs/SIM-INPUT-MODEL.md`. It writes
`@State` and re-renders after every frame. The final render goes to a PNG.
No GPU, no Mac, no phone. All our own code. The demo app
`sdk-free/swiftui/HelloApp.swift` is unchanged.

## What was built

- `App.main()` gains `--frames`. Without it, the app renders once, as in M2.
- The frames loader accepts frames of finger records and the short form
  `{"tap": [x, y]}`. The short form expands to a began frame and an ended
  frame 80 ms apart. It refuses out-of-order `t_ms`, empty `fingers`, and
  bad records, and names the frame index.
- One layout pass now places every node. The draw pass and the hit testing
  read the same placed rects, in draw order. Buttons get ids in tree order:
  `Button#1`, `Button#2`. A button draws its label only, as in M2. The hit
  area is the label rect.
- The touch rules: the topmost element under the first finger at `began`
  owns the whole touch. It keeps the touch when the finger leaves. All
  fingers of one gesture share that target. The action fires only when the
  last finger ends inside the target. A `cancelled` finger kills the
  gesture.
- `@State` boxes are pooled by creation slot. Every render pass rebuilds
  the whole tree, app included, and each pass creates the wrappers in the
  same order, so a box claimed in an earlier pass is reused at the same
  slot. A write inside an action closure shows in the next render, in child
  views and on the App struct alike. The setter stays `nonmutating`, which
  is why `{ count += 1 }` compiles unchanged. The log lists every `@State`
  value reachable from the scene and the app, by reflection.
- The runner prints each button rect, then one log line per finger record,
  after the frame's re-render succeeds.
- Font: the five descender glyphs `g j p q y` gained two rows below the
  baseline. Now `taps` and `tap me` read correctly. Text with a descender
  measures 9 points tall. This changed the M2 golden; `golden/demo1.png` was
  regenerated. The new golden `golden/after-tap.png` holds the demo render
  after one tap.
- `simview/Sources/M3App/M3App.swift` is the second app the test rows need.
  It has two buttons. Button#1 carries the state in its label, so a tap
  changes pixels inside the button box. `simview/test-m3.sh` runs the eight
  spec rows, the demo tap, the negative control, and determinism. Their
  expected results, committed before the input code, are in
  `simview/TESTS-M3.md`.

is reached through a private copy of the repo arch runner, with this

## Review round two

The first review landed as a squash merge of the original head, so the fix
commits moved to a new pull request. The reviewer named three implementation
changes that could survive rows 0 to 10. Rows 11 to 13 now cover them, and
each row was proven against a changed build: the change was applied to a
copy of the module, the row's binary was rebuilt, and the row's check
failed.

- Topmost order. A button whose label is another button gives both buttons
  the same rect. Row 11 (`overlapapp`): the inner button, drawn last, takes
  the touch, and the log says `target=Button#2`. With the hit test walking
  draw order forward, the mutant log has no `target=Button#2` line.
- Shared target. Two fingers down on two different buttons share the target
  of the first. Row 12: all six lines say `target=Button#1`, all
  `state=count:0`. With per-finger targets, the mutant logs
  `target=Button#2` lines.
- Stationary bookkeeping. A runner that rebuilds the down set from each
  frame and drops stationary fingers fires while finger 0 is still down.
  Row 13: no fire at the first lift, one action on the last lift. The
  changed build fired early; its log carried the early `state=count:1`.

Rows 9 and 10 cover the state pooling fixes, not these three; the pull
request body says so.

A second review round on the follow-up pull request found one more defect:
the state walk followed reference cycles, so an app holding a
self-referencing object crashed the walk. Fix: the walk records visited
class instances by identity and stops at each one a second time. The check
for value types had to key off the mirror display style, because
`as? AnyObject` succeeds for every boxed value and heap addresses of
short-lived boxes get reused. Rows 9 and 10 double as the check: `nestedapp`
now holds a self-referencing object, and every log line walks past it.
Removing the visited-object check segfaults row 9 (exit 139, then a
segmentation fault report).

## Review round one (first pull request)

The automated reviewer found three defects after the first push. The
findings were real. Each fix has a check.

- Nested state. A child view with its own `@State` used to get a fresh box
  on every rebuild, so its tap was logged but the render kept the initial
  value. Fix: every pass rebuilds the tree from scratch and `@State` boxes
  are pooled by creation slot. Row 9 guards it.
- App state. The scene was built once before the loop, so `@State` on the
  App struct never reached a render. Fix: the loop rebuilds `Self()` and
  the scene each pass. Row 10 guards it.
- Builder flattening. The three-child result builder nested two children in
  an inner tuple. The stack pass treated the pair as one child, so the
  configured spacing was missing between them. Fix: tuples flatten
  recursively before measure and layout. The `m3app` rects moved by the
  restored 16 point spacing; the probe keeps the tests at the new spots.
  Rows 0 to 8 pass unchanged. The demo goldens still compare at 0 differing
  pixels, because the demo tree was already flat.

## Not claimed

- No iOS gesture recognizers. The hit testing and the touch rules are ours.
- No scroll, fling, pinch, rotate, or momentum. The frame format fits them;
  the runner does not.
- No keyboard, no focus, no text input.
- No timing feel. Times come from the file, not from a clock.
- No proof about Apple's renderer. The draw path is ours.
