# M4: scripted frames push and pop a navigation stack on Linux

2026-10-11. `simview/` on branch `simview-m4`. The module gains
`NavigationStack`, `NavigationLink`, `List`, and `navigationTitle`. The
`navdemo` app draws a two-row list under a navigation bar, pushes a per-row
detail screen that owns `@State`, pushes a third screen, and pops one level
per back tap, all driven by the M3 frames file. No GPU, no Mac, no phone.
All our own code. Expected results, committed before the input code
(commit `4514bf3`): `simview/TESTS-M4.md`.

## What was built

- Spec cases `.link`, `.titled`, `.hairline`, `.navstack`.
  `NavigationStack._simSpec()` rewrites `.link` nodes into buttons whose
  action appends the destination builder to a `@State` path; the top screen
  is rebuilt through that builder every pass, so destination `@State` keeps
  its pooled box and re-renders. The back button pops with `removeLast`.
- Layout: the bar is 44 points tall; the title centers in it; the back
  button `< Back` sits at x 12 and its hit area is its label rect, like
  every M3 button; a 1 point separator line spans the bar at y 43; content
  centers in the area below. `List` is a leading stack with a separator
  after each row. A `<` glyph joined the font; a `#E5E5EA`-ish gray joined
  `Pixel`.
- `ViewBuilder.buildBlock` gained a four-child case; `Detail` has four
  children and the three-child case could not build it.
- `navdemo`: two rows (`item one`, `item two`), each a `NavigationLink` to
  `Detail(label:)` showing `detail <label>`, `taps: <n>`, a `tap` button,
  and a `deeper` link to a third screen. The source names only SwiftUI
  types, as an app would.
- Goldens: `golden/nav-root.png`, `golden/nav-one.png`,
  `golden/nav-two.png`, generated from the app itself. Tolerance in
  `simview/compare.py`: 0 differing pixels, 0 per-channel difference.

## Test results

`bash simview/test-m4.sh`, with the wrapper exported. Exit 0. Seven rows
pass; then the five mutation checks each rebuild `navdemo` against a
changed copy of the module and require the row's check to fail:

```
== mutant pop-clears: back empties the stack (row 3 must fail)
ok   mutant pop-clears failed its row
== mutant bar-wide-back: back hit rect spans the bar (row 4 must fail)
ok   mutant bar-wide-back failed its row
== mutant root-title: bar title always from the root (row 1 must fail)
ok   mutant root-title failed its row
== mutant frozen-destination: pushed spec built once at push (row 2 must fail)
ok   mutant frozen-destination failed its row
== mutant no-separators: draw skips separator lines (row 0 must fail)
ok   mutant no-separators failed its row
simview/test-m4.sh: all rows passed
```

Each mutant was checked against its documented failure, not just any
failure:

- pop-clears: the row 3 final render compares 0 differing pixels against
  `golden/nav-root.png`, so the equality with `golden/nav-one.png` fails.
- bar-wide-back: the bar tap at (250,21) logs `target=Button#1` and the
  stack empties (`state=path:[]` on the ended record).
- root-title: the row 1 render differs from `golden/nav-one.png` in the 76
  title pixels; the bar reads `demo` where the golden reads `one`.
- frozen-destination: the row 2 render does not change at all (0 differing
  pixels against `golden/nav-one.png`), so the at-least-one-pixel check
  fails while the log still says `taps:1` (the frozen spec's button still
  mutates the pooled box).
- no-separators: the row 0 render differs from `golden/nav-root.png` in
  484 pixels; the separators are gone.

## First run notes

Three suite bugs and one expectations bug failed the first runs; all were
fixed in the test script or the expectations, none in input code:

- The committed arithmetic in TESTS-M4.md sized `taps: 0`, `tap`, and
  `deeper` at 7 points; each carries a `p`, so they are 9 (the M2 descender
  rule). The pushed-screen rects and centers in the table were corrected
  with the code commit; the root screen and bar numbers were right.
- Row 2's pixel check passed vacuously against the frozen-destination
  mutant: "every differing pixel inside the box" is true when there are
  none. It now requires at least one differing pixel inside the box and
  none outside, the same lesson as M3's row 1 (`inbox >= 1`).
- The M4 log-shape regex said `state=\S+`, but a two-builder stack prints
  `path:[(Function), (Function)]` with a space; TESTS-M4.md never claimed
  the state field was space-free, so the regex now allows any characters
  before `render=ok`.
- Compare calls were handed the `/work` path on the host (the M3 scripts
  keep `$b` for binary arguments and `$bh` for host-side compares); and one
  mutant frames file was passed the host path. All runs go through the
  wrapper with `$b` arguments and host-side reads through `$bh`.

## Not claimed

- No UINavigationController parity. Push and pop are our array and our
  re-render; there is no interactive gesture pop, no large title, no
  scroll-edge effect, no animation.
- A popped destination's `@State` boxes stay pooled, so a re-push continues
  from the old value; real iOS resets it. No test exercises that path.
- One `NavigationStack` per scene; a `NavigationLink` outside a stack
  crashes by precondition; a popped screen's builder is stored, so the
  destination view value must stay capturable.
- The stand-ins table rows in the ladder doc (name registry, app data
  folder, locale, TLS) were not built: nothing in our SwiftUI module calls
  a system service, so the exit demo does not need them. They stay listed
  for Route A.
- No proof about Apple's renderer or navigator; the bar, rows and push
  semantics are ours.
