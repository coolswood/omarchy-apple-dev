# M7 rows and padding test results

2026-10-15. The simview module gained `HStack`, `Spacer`, and `.padding(_:)`.
Before this, a screen could only stack views vertically. The rules and the
test rows are in `simview/TESTS-M7.md`. Checked on the Arch chroot build
host with `swiftc`, no GPU, no Mac, no phone.

## Defects found while building it

- The first run of `test-m7.sh` showed row 2 failing with an empty ink box.
  The suite ran Python on the host with a chroot path. The helpers now map
  `$b` to the host path first. This is the same split the older suites use.
- The first nav row passed a host path to the app. The app could not read the
  frames file. It now passes the chroot path.
- Mutants first "failed" before any golden existed, because the compare crashed
  on a missing file. That is a false pass for a mutant. They count only after
  the goldens exist. The final run above is after the goldens.

## NavigationLink inside a row

The stack rewrites a link into a pushing button. It must walk rows and
padding to find the link. A one-time build of the module with those two cases
removed from the rewrite crashed `rownavdemo` at the tap with an illegal
instruction. That is the stack's own check for a link outside a stack. With
the cases in place, row 6 passes: the tap pushes, and state shows
`path:[(Function)]`.

## What stays out

No `alignment:` argument, no `Spacer(minLength:)`, no per-edge padding, no
`frame`, no `Divider`, no vertical `Spacer`. A call that uses one does not
compile. The width a spacer row fills follows our rule. Apple proposes the
parent's width, so the two can differ in a nested stack. We did not measure
that. Nothing here claims behavior of a real phone or Apple's layout.
