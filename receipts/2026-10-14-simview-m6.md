# M6 keys and text field focus test results

2026-10-14. The simview runner now reads two new frame record kinds. A `key`
record carries a USB keyboard usage number, page 7. A `text` record carries
one character. The runner routes both to the focused text field only. The M3
tap rules decide focus: the target is fixed at `began`, and a tap completes
only when the last finger ends inside the target. A completed tap focuses a
field. A tap that ends outside its target changes nothing. A tap that began
on nothing blurs. A cancelled tap changes nothing. A record with no focus is
dropped with one warning line. The module gained `TextField`. It renders its
text or placeholder, an underline, and a caret. This is our input model, not
Apple's keyboard.

## Review defect: focus without the end-inside check

Code review found one defect at `e6d673fa`, and the open Codex thread named
the same one. The `.ended` branch set `focusField` without the end-inside
check that the docs promise. Outside a scroll view nothing cancels a slide.
So a finger that went down on a field, slid off, and lifted elsewhere still
focused that field. Reproduced with a frame file on `e6d673fa`: tap field
one, type A, begin on field two, slide to empty space, lift, type B. The log
showed `text=B field=Field#2 state=first:A,second:B`. The documented result
is `first:AB`.

Fix: in `.ended`, a field focus needs the end point inside the field. A blur
needs either a completed button tap or a gesture that began on nothing. A tap
that ends outside its target changes nothing. The fix shares the end-inside
check with the button action path, which the M3 rows cover.

The two new rows were written first and failed on `e6d673fa`:

```text
FAIL row 11 slide off a field
ok   row 12 tap ending inside field two focuses it
FAIL no-end-inside mutant failed to build
simview/test-m6.sh: FAILED
```

Row 12 is the positive control: it passes on the old code and holds the fix
back from over-correcting. The `no-end-inside` mutant does not exist before
the fix, because the checked expression is the fix.

## Button case note

`keysdemo` has no button, so no M6 row drives the button-plus-focus path. The
rule is one shared end-inside check: the button branch is the same code shape
the M3 rows already cover (a press that leaves the button never fires), and
the field rows here cover the field side.

## What stays out

No shift or caps lock, and no modifier state. No IME, dictation, or
autocorrect. No caret placement by tap. No text selection. No scrolling
inside a field. Nothing here claims behavior of a real phone or its keyboard.
